Same tools as Ask/Investigate, but a genuinely more thorough pass -- more iterations budgeted, and told to verify against primary sources and try a second query rather than settle for the first result. Slower and more expensive; use it when a quick answer isn't enough.

Same tools as Ask/Investigate/Deep Dive, but pointed outward at the wider RFC landscape instead of one draft's own history -- told to proactively use the whole-corpus search tools (Citation Match, Topic Match/BM25, obsoletes/updates) to find and cite other RFCs connected to the one in question, and explain what changed across that family. A new, separate tier -- Deep Dive is unchanged and still the right choice for verifying one RFC's own history deeply. Good for "what's the bigger picture behind X" questions, e.g. "What's the broader RFC family behind RFC 6378's linear protection design, and how was it corrected in later RFCs?"

Prototype with entirely fabricated data -- no real RFCs, no real emails (see services/family_search_demo_service.py). Proves the workflow shape before importing a real family's worth of mailarchive data: check one RFC's own mail archive, and if nothing relevant turns up, rank its relatives by likely relevance and ask before checking the next one, one hop at a time. Motivating case: DNSSEC-style families, where a later RFC often explains a decision an earlier one made that its own mail archive never discusses.

Click "Load overview graph" below when you want it -- it isn't fetched or laid out automatically, since a cold build takes a couple of minutes and laying out ~9,930 nodes client-side takes real time too, not worth paying every time this tab is merely opened.

Starts from one RFC and expands outward hop by hop: hop 1 is its direct obsoletes/updates/ Citation Match/Topic Match connections, hop 2 adds their connections too, hop 3 one ring further. Citation Match (real citations, filtered to an exact keyword match) and Topic Match (whole-corpus BM25 text ranking, catches relatives Citation Match's exact match misses) are only computed for the RFC you focus on, not for its neighbors -- "shares this RFC's topic" isn't a well-defined idea two hops removed from it.
