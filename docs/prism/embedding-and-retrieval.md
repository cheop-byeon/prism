# Embedding & retrieval infrastructure

A custom embedding model (`RFC-DRAlign-QN`) fine-tuned for aligning draft/RFC text with the mailing-list discussion behind it, quantized to GGUF and served via a host-level Ollama install (validated at cosine 0.985–0.9998 against the fp16 reference) — see [Local development](../../README.md#local-development) for how it's registered. This is the same draft-to-email alignment task the mailarchive retrieval in [Decision → Discussion](decision-bot.md) depends on, so a low raw-score rank isn't a register mismatch the model wasn't built for — the retrieval-quality gap that pipeline's LLM judge exists to close has a different, not yet fully diagnosed cause.

## Mailarchive retrieval: BM25, not semantic

`api/scripts/agentic_rag/ask_decision_agent.py`'s `_MAILARCHIVE_REGISTRY` (both drafts it currently supports, LEDBAT and sidr) uses BM25/economy datasets, not semantic/hierarchical ones, despite semantic being tried first for both. A rigorous side-by-side comparison — raw retrieval rank at top_k=50 (the tool's real default), plus full end-to-end answer quality, on identical source content for both approaches — showed BM25 reliably places the actually-relevant message at or near rank 1 with the large majority of hits substantive, while semantic search either buried it past rank 40 or missed it in the top 50 entirely, with most hits under 300 characters of decontextualized noise.

The natural explanations don't hold up under a follow-up isolation test: it isn't chunk size (large ~4096-token parent segments showed a *narrower*, not wider, similarity spread than the small child chunks actually indexed), and it isn't `RFC-DRAlign-QN` specifically being a poor fit (`nomic-embed-text`, a general-purpose model, showed the same relative score spread on the identical chunks). The more likely explanation: this corpus is topically homogeneous (one WG's mailing list, one jargon vocabulary), so cosine similarity mostly captures domain/topic resemblance rather than the fine-grained "is this the specific decision" signal a query needs — any embedding model, at any chunk size, would likely compress near the top of a corpus this narrow. BM25's exact-phrase matching doesn't have that problem, since it's a sharp binary signal rather than a smoothly-varying topical one.

If semantic retrieval is revisited for this corpus, the evidence here points away from re-tuning chunk size or swapping embedding models, and toward a fundamentally different approach: a cross-encoder reranker (scores query+passage jointly) or hybrid BM25+semantic, since those are built to resolve fine-grained relevance within a narrow domain rather than relying on independently-computed embedding distance.

## Per-dataset keyword store

Stock Dify's Economical (keyword-only) indexing mode only had Jieba, a TF-IDF-style overlap ranker. Migration `a1b2c3d4e5f6_add_keyword_store_to_datasets` adds a `datasets.keyword_store` column (default `'bm25'`), and `Keyword._init_keyword()` now prefers that per-dataset value over the old server-wide config. `api/core/rag/datasource/keyword/bm25/bm25.py` is a from-scratch `Bm25Keyword` implementation: it stores the full tokenized corpus in the existing keyword-table storage slot, tokenizes with a minimal regex + ~90-word stopword list (no NLP dependency), ranks with `rank_bm25.BM25Plus` computed per query, and guards concurrent index updates with a Redis lock. It's selectable per dataset via a radio control shown when Economical mode is chosen in the create-dataset wizard.

## Weaviate hardening

Weaviate's hybrid/BM25 full-text search already existed in stock Dify — what this fork changed is correctness under the new [chunking strategies](chunking-strategies.md): chunk UUIDs are now derived from each chunk's own `doc_id` instead of a hash of its text, since identical short chunks (common with paragraph/semantic/framework splitting) were colliding and silently overwriting each other under the old content-hash scheme; metadata keys that would collide with Weaviate's own reserved properties (`id`, `vector`) are now guarded against; differently-named source fields (`message_id`/`messageId`, `source_url`/`link`, etc.) are canonicalized into a fixed set of display properties; and a new `get_by_ids()` method fetches chunks by ID for [chunk metadata inspection](chunk-metadata.md).
